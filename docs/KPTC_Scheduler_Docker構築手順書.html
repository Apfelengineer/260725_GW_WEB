1. 構成と情報の流れ

初期運用はOriginサーバー1台です。Scheduler・JSON配信担当・静的Calendarの3コンテナを動かします。将来はCalendarだけをTamanegiへ移し、配信担当の設定をlocalからsftpへ変更します。

担当実行環境・役割参照できる情報
SchedulerPHP 8.4＋Apache。予定の保存、認証、公開JSONの生成。内部SQLite・バックアップ・公開用出力。
配信担当Python＋OpenSSH。JSONを検証し、local書込みまたはSFTP転送。外部からの受付ポートなし。公開JSONと配信状態だけ。分離時のみ転送鍵。SQLiteはマウントしない。
CalendarNginx。HTML・CSS・JavaScript・画像・JSONの静的配信。公開用JSONを読取り専用で参照。PHP・SQLite・秘密鍵なし。

1-1. 詳細論理構成図

既存社内システム → Scheduler【Origin・社内向け】社内システムがCBC tokenを発行。Schedulerが検証し、予定表を表示。renkonは検証用の模擬入口。本番への配置は不要。
Scheduler専用の非公開VolumeSQLite ＋ 毎日22時の最新JSONバックアップこの領域をCalendar・配信担当へ共有しません。
Scheduler → 公開用出力Volume（kptc-outbox）当月を含む3か月分の室名・画像名・日別状態だけ。氏名・予定件名・メモ・認証情報なし。Schedulerが書込み、配信担当は読取り専用。
JSON配信担当【Origin】形式・期間・世代・更新日時を検証。失敗しても内部予定の保存は成功させ、30秒間隔で再試行。配信状態Volume：配信担当が書込み、Schedulerが読取り専用で参照。
方式A：local【初期運用】配信担当 → 公開JSON専用Volume → Originの静的Calendar → 閲覧者配信担当はネットワークなし。Calendarは公開JSONを読取り専用マウント。
方式B：sftp【将来の分離】Origin配信担当 → SFTP → TamanegiのJSON専用フォルダ → 静的Calendar → 閲覧者接続開始はOriginだけ。TamanegiからOriginへの新規接続を許可しない。秘密鍵はOriginの配信担当だけが保有。

CalendarからScheduler専用Volumeへの接続経路はありません。同一サーバーでも共有するのは公開JSONだけです。別サーバーでも内部DBを公開したり、Tamanegiから取りに来させたりしません。

画面が取得する固定URLは./data/public-availability.jsonです。公開用3か月JSON（単一ファイル）を更新し、過去月のファイルは増やしません。ファイルの更新日時が30分を超えた場合は注意を表示し、当月から3か月分が揃っていない場合は空きと誤表示せず準備中とします。

URLと実フォルダ：/Scheduler/・/Calendar/はプロキシ側の公開パスです。コンテナはルート/で動作します。ブラウザがOriginへ直接接続する場合はhttp://origin:8080/・http://origin:8081/です。大文字・小文字を区別してください。

簡易参考資料：docker/README.md。詳細な構築作業は本HTMLを参照してください。

2. 事前準備

  • Ubuntu 24.04のOriginと、sudoを使える作業アカウント。
  • Origin内部IP・利用者の公開URL・リバースプロキシのIPを管理者に確認。
  • 社内システムと同じtoken鍵の固定文字列。実値をGitHubや資料へ記載しない。
  • 分離時はUbuntu 24.04のTamanegi、SFTP接続許可、公開ホスト名・証明書も準備。

本書はDocker Composeによる構築を標準とします。Tamanegiに既存のWordPress等がある場合、カレンダーは独立コンテナ・独立データフォルダに置き、既存サイトのファイルを上書きしません。

既存運用がある方：初期設定例を実環境envへ上書きしないでください。まず9章の移行手順を確認します。

5. 環境設定

5-1. Originの待受IP

cd /opt/kptc/260725_GW_WEB

nano .env

5-4. HTTPとHTTPSの切替

設定直接HTTPプロキシ経由HTTPS
入口のScheduler URLhttp://origin:8080/https://公開名/Scheduler/
Cookie Path//Scheduler/
Cookie Secure01
カレンダーリンクhttp://origin:8081/https://公開名/Calendar/

env変更後はコンテナの再作成が必要です。envだけなら再ビルドは不要です。

sudo docker compose -f compose.origin-single.yaml config --quiet
sudo docker compose -f compose.origin-single.yaml up -d --force-recreate

HTTPSは管理者のリバースプロキシで証明書を配置して終端します。443番の許可、必要に応じた80番から443番への転送、tokenのクエリ文字列・Cookie・X-CSRF-Tokenの保持が必要です。X-Forwarded-Proto: httpsを渡します。ブラウザ側がHTTPSなら、プロキシからOriginがHTTPでもSecureは1です。

直接HTTPでもプログラムは動作しますが、token・Cookieの盗聴リスクが残ります。管理者がネットワークの許可範囲を確認し、実運用ではHTTPS化を推奨します。

6. 同一サーバーで構築・起動

cd /opt/kptc/260725_GW_WEB
sudo docker compose -f compose.origin-single.yaml config --quiet
sudo docker compose -f compose.origin-single.yaml build --pull
sudo docker compose -f compose.origin-single.yaml up -d

3コンテナが起動します。CalendarのhealthyはWeb配信プロセスの正常性だけを示します。初回はJSONがないため画面が準備中になります。8章の手順で初回生成・配信を確認します。

curl -i http://Origin内部IP:8080/
curl -i http://Origin内部IP:8081/healthz
sudo docker compose -f compose.origin-single.yaml logs --tail 100

tokenなしSchedulerがHTTP 403、Calendarの/healthzがHTTP 200なら入口は正常です。データの正常性は別途監視します。

データ保持：docker compose down -vはDB等のVolumeを削除します。更新や切替で実行しません。

7. リバースプロキシ管理者への特記事項

リバースプロキシの導入・設定変更はサーバー管理者が別途実施します。本作業で仮想リバースプロキシは構築しません。

外部パス初期運用の中継先アクセス制御
/Scheduler/http://Origin内部IP:8080/許可された社内IPのみ。
/Calendar/http://Origin内部IP:8081/一般公開。分離後はTamanegiの静的配信ポートへ変更。
  • 上記接頭辞を取り除いて各コンテナのルートへ中継。末尾スラッシュへの転送でもtokenを保持。
  • SchedulerはGET・POSTとCookie、X-CSRF-Tokenを保持し、APIをキャッシュしない。
  • CalendarはGET・HEADだけ。PHPやWordPressへフォールバックさせない。
  • /Calendar/data/public-availability.jsonは/data/public-availability.jsonへ転送。JSON・index.htmlをキャッシュしない。現行の静的コンテナは全ファイルへCache-Control: no-storeを設定。
  • /healthzは静的Webサーバーの稼働確認であり、JSON鮮度の保証ではない。
  • Host、X-Forwarded-For、X-Forwarded-Protoを保持。SchedulerのPOST上限は少なくとも2MB。
  • CalendarコンテナにはPHPハンドラーなし。.php・隠しファイル・任意のdataファイルは404。ディレクトリ一覧も無効。
  • 既存HPへiframeで組み込む場合、標準のframe-ancestors 'self'は別ドメインを拒否するため、管理者が必要な親サイトだけをCSPへ追加。

Originの8080・8081番はプロキシと許可端末だけに制限します。分離後はTamanegiからOriginへの新規接続を禁止し、Originの配信担当からTamanegiのSFTPポートだけを許可します。SFTPの応答通信は必要です。

8. 初期設定と動作確認

8-1. 初期DBと管理者パスワード

SQLite用DBサーバーの導入は不要です。社内入口から最初にアクセスすると、PHPがVolume内へSQLiteのファイルと表を自動作成します。正しいtokenを付けて社内入口から1回開いた後に実行します。

sudo docker exec -it kptc-scheduler \
  php /var/www/html/manage-auth-user-cli.php set-admin-mode-password

8〜128文字のパスワードを入力します。文字は表示されません。実値をチャットやコマンド引数へ書きません。

8-2. JSONの生成と配信は別々に確認

sudo docker exec kptc-scheduler php /var/www/html/publish-availability-cli.php
sudo docker compose -f compose.origin-single.yaml logs --since 5m kptc-publisher
curl -i http://Origin内部IP:8081/data/public-availability.json
sudo docker exec kptc-scheduler php /var/www/html/monitor-availability-cli.php

queued:trueは「生成済み」であり「公開済み」ではありません。配信担当が30秒以内に検証・配信します。配信ログのok:true、JSONのHTTP 200、内部監視の終了コード0を確認してからブラウザを再読み込みします。

配信確認を待たずすぐ実行する場合は、常駐プロセスと同じ鍵・Volumeを使う次のコマンドを実行します。二重処理はロックで防ぎます。

sudo docker compose -f compose.origin-single.yaml exec kptc-publisher \
  python /opt/kptc/delivery.py --once

予定の保存後に共有済みとなる、再読み込み後も予定が残る、管理者切替後も保存できる、室の予定変更が公開JSONへ反映されることを確認します。何も操作しない間にsave-deltaが繰り返されないことも確認します。

9. 旧版の移行とTamanegiへの分離

9-1. PHPカレンダー版から同一サーバー静的版へ

  1. 10章の方法でDBとenvのバックアップを非公開領域へ確保。公開ファイルの上書き前に戻し方を確認。
  2. 最新版を取得。手動変更がある場合はgit statusで確認し、強制リセットせず差分を整理。
  3. 既存scheduler.envのtoken鍵・Cookie・DB設定を維持し、5章の出力JSONと状態JSONのパスを追加。
  4. publisher.envを新規作成しlocalを設定。新しい公開専用VolumeはJSONを再生成するため、旧公開JSONの移植は不要。
  5. 6章で3コンテナを再ビルド・再作成。8章の生成・配信確認を実施。
  6. プロキシの公開JSON URL・PHPキャッシュ設定を7章へ合わせる。利用者は古いタブを閉じ、入口から開き直す。

旧設定のKPTC_PUBLIC_AVAILABILITY_MODE・ENDPOINT・SECRET・ALLOW_HTTP・TIMEOUT（いずれも同じ接頭辞）は静的版で使いません。旧calendar.env、PHP受信APIとヘルスAPIも廃止です。旧Volumekptc-calendar-dataは参照しませんが、自動削除はしません。kptc-scheduler-dataは同名のまま引き継ぎます。

Dockerを使わず配布ファイルを直接配置する場合も、PHP版フォルダへそのまま重ねず、新しい静的フォルダを準備して切り替えます。旧.php・.user.iniを新しい公開フォルダへ持ち込みません。公開JSONをdata/public-availability.jsonへ配置します。

さくら共有サーバーにはDocker・Pythonがないため、非公開領域の01_source/publisher/delivery-local-cli.phpを使います。PHPを実行するのは内部の配信処理だけであり、Calendarは静的ファイルのみです。生成5分・配信1分・監視10分の定期実行を設定し、配信先・生成先・状態ファイルを別々に指定します。詳細はREADMEの「さくらインターネットへの配置」を参照してください。この共有サーバー用補助処理は、UbuntuのPython配信コンテナや将来のSFTP構成を置き換えるものではありません。

9-2. Tamanegiに静的カレンダーを準備

ここからは将来分離するときだけ行います。Tamanegiにも3章のリポジトリを/opt/kptc/260725_GW_WEBへ取得します。Originとは別のコンピューター上にある同名パスです。Tamanegiで使用するのは静的Calendar・設定だけで、Schedulerを起動しません。

Tamanegiで実行します。既存HPと重ならない名前・ポート・フォルダであることを先に確認します。

sudo apt update
sudo apt install -y openssh-server
sudo useradd --system --user-group --home-dir /data --shell /usr/sbin/nologin kptc-upload
sudo install -d -o root -g root -m 755 /srv/kptc-calendar
sudo install -d -o kptc-upload -g kptc-upload -m 755 /srv/kptc-calendar/data
sudo install -d -o root -g root -m 755 /etc/ssh/authorized_keys
cd /opt/kptc/260725_GW_WEB
cp compose.env.example .env
nano .env

Tamanegiの.envへ待受IPを設定します。プロキシがTamanegi内なら127.0.0.1、別ホストならTamanegi内部IPを使います。

KPTC_CALENDAR_BIND_ADDRESS=127.0.0.1
sudo docker compose -f compose.tamanegi.yaml config --quiet
sudo docker compose -f compose.tamanegi.yaml build --pull
sudo docker compose -f compose.tamanegi.yaml up -d
sudo docker compose -f compose.tamanegi.yaml ps

既存HPのPHP実行ユーザーには/srv/kptc-calendar/dataへの書込み権限を与えません。公開コンテナは同フォルダを読取り専用で参照します。カレンダー用の公開URLを、既存HPのWordPress書換えから独立してプロキシへ設定します。

9-3. Originで転送専用鍵を作る

sudo install -d -m 700 /etc/kptc/sftp
sudo ssh-keygen -t ed25519 -f /etc/kptc/sftp/id_ed25519 -N '' -C kptc-calendar-delivery
sudo chown -R 1000:1000 /etc/kptc/sftp
sudo chmod 700 /etc/kptc/sftp
sudo chmod 600 /etc/kptc/sftp/id_ed25519

自動処理用なので鍵にパスフレーズは設定しません。その代わりに専用ユーザー・接続元制限・最小権限を必ず組み合わせます。UID1000は配信コンテナの実行ユーザーです。鍵をScheduler・Calendar・GitHubへコピーしません。

公開鍵id_ed25519.pubだけを管理者経由でTamanegiへ渡し、次の固定パスへ所有者root・権限644で保存します。公開鍵は秘密情報ではなく、SSHが転送ユーザーとして読める必要があります。秘密鍵は渡しません。

# Tamanegiで実行。/tmp/kptc-delivery.pub は受け取った公開鍵。
sudo install -o root -g root -m 644 /tmp/kptc-delivery.pub /etc/ssh/authorized_keys/kptc-upload
sudo cp docker/tamanegi/60-kptc-upload.conf.example /etc/ssh/sshd_config.d/60-kptc-upload.conf
sudo sshd -t
sudo systemctl reload ssh

この設定は転送専用ユーザーだけを/srv/kptc-calendarへ隔離し、通常のシェル・ポート転送を禁止します。chrootから見える/dataが実際の/srv/kptc-calendar/dataです。既存の管理者SSH接続を開いたまま、別接続で確認してから終了してください。

9-4. 接続先ホスト鍵を確認する

Originで候補を取得します。tamanegi.example.jpは実ホスト名へ変更します。

sudo sh -c 'ssh-keyscan -t ed25519 -p 22 tamanegi.example.jp > /etc/kptc/sftp/known_hosts'
sudo ssh-keygen -lf /etc/kptc/sftp/known_hosts

Tamanegi側で次を実行した結果の指紋と、別経路で一致を確認してください。ssh-keyscanだけでは相手が本物か確認できません。

sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

一致確認後、Originで権限を設定します。ホスト鍵が変更された場合は原因確認後に更新し、確認機能を無効にしません。

sudo chown 1000:1000 /etc/kptc/sftp/known_hosts
sudo chmod 600 /etc/kptc/sftp/known_hosts

9-5. localからsftpへ切り替える

管理者が、OriginからTamanegiのSFTPポートだけを許可し、TamanegiからOriginへの新規接続を禁止します。TamanegiのSSH受付は既存管理者の接続を維持しつつ、転送についてはOriginのIPだけに限定します。

Originの/etc/kptc/publisher.envを変更します。

KPTC_AVAILABILITY_DELIVERY_MODE=sftp
KPTC_AVAILABILITY_INTERVAL=30
KPTC_PUBLIC_AVAILABILITY_STALE_SECONDS=1800
KPTC_AVAILABILITY_SFTP_HOST=tamanegi.example.jp
KPTC_AVAILABILITY_SFTP_PORT=22
KPTC_AVAILABILITY_SFTP_USER=kptc-upload
KPTC_AVAILABILITY_SFTP_DIRECTORY=/data

カレンダーリンクを切り替える前に、配信担当だけをsftp版へ切り替えて試験します。旧Calendarはこの時点では停止しません。

cd /opt/kptc/260725_GW_WEB
sudo docker compose -f compose.origin-single.yaml stop kptc-publisher
sudo docker compose -f compose.origin-split.yaml config --quiet
sudo docker compose -f compose.origin-split.yaml up -d --build kptc-publisher
sudo docker exec kptc-scheduler php /var/www/html/publish-availability-cli.php
sudo docker compose -f compose.origin-split.yaml exec kptc-publisher python /opt/kptc/delivery.py --once
sudo docker exec kptc-scheduler php /var/www/html/monitor-availability-cli.php

Tamanegiの公開URLで/Calendar/data/public-availability.jsonがHTTP 200になり、室名・期間・更新日時が正しいことを確認します。成功後、scheduler.envのリンク先を変更します。

KPTC_PUBLIC_AVAILABILITY_PAGE_URL=https://tamanegi.example.jp/Calendar/
sudo docker compose -f compose.origin-split.yaml up -d --force-recreate kptc-scheduler
sudo docker compose -f compose.origin-split.yaml ps
# Tamanegi側で表示を確認した後にだけ、Originの旧Calendarを停止
sudo docker compose -f compose.origin-single.yaml stop kptc-calendar

以後、Originはcompose.origin-split.yaml、Tamanegiはcompose.tamanegi.yamlを使います。両サーバーで同じ配信先へ複数の配信担当を起動しないでください。将来部屋を追加する際の画像は、静的Calendarの配布物にも追加します。

localへ戻す場合：Originのpublisher.envをlocalへ戻し、公開リンクもOriginへ戻します。compose.origin-single.yaml up -d --force-recreateで3コンテナを再作成し、8章で確認します。DBとJSON出力Volumeは共通で保持されます。

10. 更新・復元・バックアップ

10-1. 通常更新

基本は開発用PCで修正 → 試験 → ビルド → GitHubのmainへ反映 → サーバーで再構築です。サーバー上で01_sourceや配布JSを直接修正しません。手動修正がある場合は先にgit status・git diffで整理し、envは作り直さず維持します。

初期構成ではOriginで実行します。YYYYMMDD-HHMMは更新日時に置き換えます。

cd /opt/kptc/260725_GW_WEB
git status
git fetch origin
git switch main
git pull --ff-only origin main
sudo docker image tag kptc-scheduler:latest kptc-scheduler:rollback-YYYYMMDD-HHMM
sudo docker image tag kptc-publisher:latest kptc-publisher:rollback-YYYYMMDD-HHMM
sudo docker image tag kptc-calendar:latest kptc-calendar:rollback-YYYYMMDD-HHMM
sudo docker compose -f compose.origin-single.yaml build --pull
sudo docker compose -f compose.origin-single.yaml up -d --force-recreate
sudo docker compose -f compose.origin-single.yaml ps
sudo docker compose -f compose.origin-single.yaml logs --since 10m

分離後はOriginでcompose.origin-split.yaml、Tamanegiでcompose.tamanegi.yamlを使い、それぞれ同じ版のリポジトリを取得して更新します。Tamanegiへ内部の実環境ファイルを転送しません。PHP・Python・Nginx・OpenSSHの更新確認も必要で、単なる再起動ではランタイムは更新されません。

10-2. 更新前のSQLite退避

更新操作の前に実行してください。SQLiteのバックアップAPIで、使用中でも整合したファイルを作成します。

sudo docker exec kptc-scheduler php -r '
$source = new SQLite3("/var/lib/kptc-scheduler/group-watcher.sqlite", SQLITE3_OPEN_READONLY);
$target = new SQLite3("/var/lib/kptc-scheduler/pre-update-YYYYMMDD-HHMM.sqlite");
if (!$source->backup($target)) exit(1);
$target->close(); $source->close();
'

envとSFTP鍵も管理者の非公開バックアップ先へ退避します。公開フォルダやGitHubへ保存しません。

10-3. JSONバックアップからSQLiteへ復元

毎日22時に、当日以降に終了する予定をscheduler-latest.jsonへ上書きします。過去版は残しません。復元ツールは新しいSQLiteを作成し、本番DBを直接上書きしません。

sudo docker exec kptc-scheduler php /var/www/html/restore-scheduler-cli.php \
  /var/lib/kptc-scheduler/backups/scheduler-latest.json \
  /var/lib/kptc-scheduler/restored-YYYYMMDD-HHMM.sqlite

復元成功後、利用者の操作を停止し、Schedulerを停止して切り替えます。分離後はCompose名を変更します。対象日付をすべて同じ値へ置き換え、既存の同名退避がないことを確認します。

sudo docker compose -f compose.origin-single.yaml stop kptc-scheduler
sudo docker run --rm -v kptc-scheduler-data:/data alpine sh -c '
set -eu
for file in group-watcher.sqlite group-watcher.sqlite-wal group-watcher.sqlite-shm; do
  if [ -f "/data/$file" ]; then mv "/data/$file" "/data/pre-restore-YYYYMMDD-HHMM-$file"; fi
done
mv /data/restored-YYYYMMDD-HHMM.sqlite /data/group-watcher.sqlite
chown 33:33 /data/group-watcher.sqlite
chmod 600 /data/group-watcher.sqlite
'
sudo docker compose -f compose.origin-single.yaml start kptc-scheduler
sudo docker exec kptc-scheduler php /var/www/html/publish-availability-cli.php

公開JSONはDBから再生成できます。復元DBの版番号が配信済みより小さくなる場合は、上記の再開・生成コマンドを実行する前に管理者が復元内容を確認します。Schedulerと配信担当を停止した状態で、outboxのpublic-availability.json・状態Volumeのstatus.json・公開先の旧JSONを非公開領域へ退避してから再開し、生成・配信してください。これは正常な情報への意図的な復旧時だけの手順です。通常運用では古い世代を自動で受け入れません。

10-4. プログラムのロールバック

DBを自動で戻す操作ではありません。同じ静的構成内の正常版へ戻す場合、3イメージのタグを戻します。

sudo docker compose -f compose.origin-single.yaml stop
sudo docker image tag kptc-scheduler:rollback-YYYYMMDD-HHMM kptc-scheduler:latest
sudo docker image tag kptc-publisher:rollback-YYYYMMDD-HHMM kptc-publisher:latest
sudo docker image tag kptc-calendar:rollback-YYYYMMDD-HHMM kptc-calendar:latest
sudo docker compose -f compose.origin-single.yaml up -d --no-build --force-recreate

PHPカレンダー旧版へ戻す場合は、Compose定義・旧envも同じ旧版に揃える必要があります。旧公開JSONは必要に応じて再生成します。日次JSONバックアップだけではサーバー全損に備えられないため、DB Volume・env・鍵は別媒体のバックアップも検討してください。

11. Webブラウザで閲覧・操作できるまで

  1. 管理者が待受IP、許可IP、必要な公開URLとHTTPSを設定。
  2. 既存社内システムがログイン済み利用者について保持しているIDをuser_xxxとし、CBC方式のBase64(IV＋暗号文)token付きURLでSchedulerへ移動。
  3. 予定の新規・編集・移動・コピー・削除、再読み込み後の保持、管理者切替を確認。
  4. 無操作で保存通信が繰り返されないこと、保存失敗時に再試行できることを確認。
  5. 公開JSONの配信確認後にCalendarを開く。3か月表示、土日祝、午前・午後・メンテナンス、画像と凡例を確認。
  6. 未許可端末のScheduler拒否、CalendarでPHPや任意のdataファイルが404となることを確認。
確認対象合格条件
内部予定共有済みになり、再読み込み後も予定を保持。
公開JSON当月を含む3か月・公開項目だけ。転送完了を監視で確認。
分離Calendarと配信担当にSQLiteなし。Calendarに鍵なし。
停止時転送障害でも内部保存は成功。古い情報に注意を表示。

12. 困ったときのQ＆A

Q1. 初期構築で「sqlite3」のインストールエラーが出る。

A. 旧Dockerfileの不備です。修正版ではsqlite3の重複インストールを外し、ビルド中に拡張の有効性を確認します。最新版を取得して再ビルドし、次で両方yesになることを確認します。

sudo docker exec kptc-scheduler php -r '
foreach (["pdo_sqlite", "sqlite3"] as $name) echo $name."=".(extension_loaded($name) ? "yes" : "no").PHP_EOL;
'

Q2. Origin外のプロキシから接続できない。

A. 同一ホストの127.0.0.1待受を想定した設定と実環境の相違が考えられます。5-1節の待受IPをOrigin内部IPへ変更してコンテナを再作成し、ファイアウォール・中継先も確認します。

Q3. 「内部サーバーへ接続できません」と表示され、bootstrapが403になる。

A. 確認済みの原因はCookieパスの不一致です。ブラウザURLがhttp://origin:8080/ならPathは/、Secureは0。HTTPSの/Scheduler/ならPathも/Scheduler/、Secureは1。env変更後にSchedulerを再作成し、古いCookieを削除して入口から入り直します。

Q4. 無操作でも保存中と共有済みが交互になり、管理者切替後に403になる。

A. 旧画面の比較処理と、待機中の保存が古いCSRFを使用する不備です。修正版は項目順を無視して比較し、保存と管理操作を直列実行して最新トークンを使います。10章で再ビルドし、古いタブを閉じて入口から入り直してください。

Q5. 予定の登録通知が出ても再読み込みで消える。

A. サーバー保存前に通知する旧版、または保存失敗が考えられます。修正版は成功後に通知し、失敗時は未保存データを保持して「再試行」を表示します。未保存のまま再読み込みせず、エラー文・save-deltaの状態コードを確認してください。

Q6. Calendarが準備中になる。

A. 初回JSONがない、配信が失敗、または当月から3か月の期間が揃っていません。8-2節で生成・配信を実行し、配信担当ログと/data/public-availability.jsonを確認します。CalendarのhealthyだけではJSONの正常性は分かりません。

Q7. 更新が遅れていると表示される。

A. 最終生成から30分を超えた、または再取得に失敗しています。Schedulerの5分ごとの生成cron、配信担当の状態、転送先の空き容量・権限を確認してください。失敗時も最後の正常データを残しますが、古い情報を予約なしとは扱いません。

Q8. SFTP転送が失敗する。

A. ホスト名・接続許可・公開鍵・ホスト鍵・保存先権限を確認します。秘密鍵はUID1000が読める権限600、chroot親はroot所有・書込み不可、dataだけ転送ユーザー所有にします。ホスト鍵不一致時に検証を無効にせず、管理者に指紋確認を依頼します。

Q9. 配信担当のVolumeに書き込めない。

A. 独自の既存Volumeやbind mountを流用して権限が違う可能性があります。標準は配信担当がUID1000、公開用・状態Volumeの所有者も1000です。新しい専用Volumeを使用し、chmod 777や内部DBの共有で回避しません。

Q10. Tamanegiに既存のPHP・WordPressがある。

A. 静的カレンダーはPHPハンドラーなしの専用コンテナへ配置し、既存HPからそのファイルへ書込みできない権限にします。共有OSのリスクは残るため既存サイトの更新も必要です。Originへの新規接続は禁止し、転送先はJSON専用領域に限定します。

Q11. コンテナの再作成後に予定が見えない。

A. 別のDB Volumeを参照していないか確認します。標準のkptc-scheduler-dataを両Origin方式で共通使用します。Volumeを削除せず、元のデータを特定し、必要なら10-3節で復元してください。

Q12. JSON更新の成功表示と公開画面が一致しない。

A. queued:trueは出力完了で、配信完了ではありません。配信担当のok:true、内部監視、公開URLの更新日時を確認します。画面は60秒ごとにJSONを再取得します。プロキシがJSONをキャッシュしていないことも確認してください。
