1. 最初に全体像を確認

結論から言うと、originとtamanegiは別々の物理サーバーまたは仮想サーバーに構築します。作業用フォルダ、Dockerコンテナ、保存領域も共有しません。

originサーバー（内部）社内だけで使うスケジューラ
SQLiteへ予定を保存
→
tamanegiサーバー（外部）外部公開する空き状況
3か月分のJSONだけを保存

originは予定を保存すると、公開してよい情報だけをJSONへ変換し、ネットワーク越しにHTTPSでtamanegiのreceive-availability.phpへ送信します。tamanegiからoriginのSQLiteへ接続することはありません。

名称役割公開範囲保存データ
origin予定の登録・編集・管理社内ネットワークのみSQLite、最新バックアップJSON
tamanegi試験室の空き状況表示インターネット公開用JSONのみ
renkon相当社内システムから認証トークンを発行既存社内システム本番では今回のDocker構築対象外
分離の原則：originのSQLiteやバックアップをtamanegiへ置かず、両サーバーで同じDockerボリュームやネットワークフォルダを共有しません。両者が共有するのは、tamanegiの受信URLとJSON署名用秘密値だけです。
大切：Dockerfileをダブルクリックして実行するわけではありません。それぞれのサーバーのターミナルでdocker build -f ...を実行します。また、docker/originなどへ移動して構築すると必要ファイルが見つかりません。必ず各サーバーの構築用フォルダ最上位で実行してください。

2. 事前に準備するもの

1サーバーとURL

次の値をサーバー管理者またはネットワーク管理者へ確認し、空欄へ記入してください。

確認項目記入欄・例
originのホスト名例：origin
originの社内URL例：https://scheduler.example.local/
tamanegiのホスト名例：tamanegi
tamanegiの公開URL例：https://calendar.example.jp/
tamanegiの受信URL公開URL＋receive-availability.php
各サーバーの管理用ユーザーsudoを使用できるユーザー

2通信と名前の設定

  • tamanegiのドメイン名が、tamanegiサーバーのIPアドレスを示している
  • tamanegiは外部からTCP 443番（HTTPS）へ接続できる
  • originからtamanegiのTCP 443番へ接続できる
  • originは社内ネットワークからだけ接続できる
  • 各URLに使用するHTTPS証明書を準備できる
IPアドレスよりドメイン名を推奨：HTTPS証明書は通常ドメイン名に対して発行されます。IPアドレスを送信先へ直接指定すると、証明書の名前が一致せず通信に失敗する場合があります。

32種類の秘密値

秘密値はそれぞれ別に作り、使い回さないでください。例として次の命令で64文字の値を作れます。

openssl rand -hex 32
秘密値同じ値を持つ場所用途
KPTC_PORTAL_TOKEN_KEYoriginと既存社内システム社内システムからoriginへ入るためのトークン
KPTC_PUBLIC_AVAILABILITY_SECREToriginとtamanegi公開JSONが正しい送信元から届いたことの確認
禁止事項：実際の秘密値、SQLite、公開JSON、パスワードをGitHubへ保存しないでください。秘密値は後述する/etc/kptc/*.envだけへ保存し、権限を600にします。

3. 必要ファイルと配置場所

3-1. originサーバーへGitHubから取得

まずoriginサーバーへ接続したターミナルで、origin専用の作業場所へ取得します。すでにGitが入っている前提です。

sudo mkdir -p /opt/kptc-origin-build
sudo chown "$USER":"$USER" /opt/kptc-origin-build
cd /opt/kptc-origin-build
git clone https://github.com/Apfelengineer/260725_GW_WEB.git
cd 260725_GW_WEB
git switch main

originサーバーでpwdの結果が/opt/kptc-origin-build/260725_GW_WEBになれば正しい場所です。

3-2. tamanegiサーバーへGitHubから取得

次に、originからログアウトしてtamanegiサーバーへ接続した別のターミナルで、tamanegi専用の作業場所へ取得します。

sudo mkdir -p /opt/kptc-tamanegi-build
sudo chown "$USER":"$USER" /opt/kptc-tamanegi-build
cd /opt/kptc-tamanegi-build
git clone https://github.com/Apfelengineer/260725_GW_WEB.git
cd 260725_GW_WEB
git switch main

tamanegiサーバーでpwdの結果が/opt/kptc-tamanegi-build/260725_GW_WEBになれば正しい場所です。originの作業場所とは別物です。

同じGitHubリポジトリを取得する理由：Dockerfileが必要とするビルド後ファイルを確実に揃えるためです。両サーバーに同じ名前のGitHubフォルダがあっても、サーバーと絶対パスが異なり、コンテナもデータも混ざりません。Dockerイメージへ入るのは各Dockerfileが指定した側のファイルだけです。

3-3. GitHubを使わず、必要ファイルだけ手作業で配置する場合

ファイル転送ソフトを使う場合は、各サーバーへ必要な側だけを置けます。フォルダ名を変えても構いませんが、Dockerfileと02_releaseの相対位置は変えないでください。

originサーバーだけに置くもの

/opt/kptc-origin-build/260725_GW_WEB/
├── .dockerignore
├── 02_release/
│   └── origin/          ← 内部スケジューラのビルド後ファイル一式
└── docker/
    └── origin/
        ├── Dockerfile
        ├── entrypoint.sh
        ├── apache-security.conf
        ├── kptc-cron
        └── origin.env.example

tamanegiサーバーだけに置くもの

/opt/kptc-tamanegi-build/260725_GW_WEB/
├── .dockerignore
├── 02_release/
│   └── tamanegi/        ← 外部カレンダーのビルド後ファイル一式
└── docker/
    └── tamanegi/
        ├── Dockerfile
        ├── entrypoint.sh
        ├── apache-security.conf
        └── tamanegi.env.example
構築先最低限必要なものDockerfileが読み込む場所
origin.dockerignore、docker/origin/、02_release/origin/02_release/origin/をコンテナの/var/www/html/へコピー
tamanegi.dockerignore、docker/tamanegi/、02_release/tamanegi/02_release/tamanegi/をコンテナの/var/www/html/へコピー
よくある間違い：cd docker/originの後にdocker build .を実行すると、02_release/originが構築範囲の外になり失敗します。originでは/opt/kptc-origin-build/260725_GW_WEB、tamanegiでは/opt/kptc-tamanegi-build/260725_GW_WEBで実行します。

4. Ubuntu 24.04へDockerを導入

originとtamanegiの両方で行います。すでに管理者がDockerを導入済みなら、最後の確認だけ行ってください。

以下はDocker公式のUbuntu向けAPTリポジトリを使う方法です。古いDockerパッケージがある環境や組織独自の管理方法がある場合は、先にサーバー管理者へ確認してください。

4-1. 公式鍵と配布元を登録

sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
  -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

sudo tee /etc/apt/sources.list.d/docker.sources >/dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF

sudo apt update

4-2. Dockerを導入

sudo apt install -y docker-ce docker-ce-cli containerd.io \
  docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
sudo docker run --rm hello-world

最後にHello from Docker!が表示されれば導入成功です。本書では権限の誤設定を避けるため、以後のDocker命令にsudoを付けます。

参照：Docker公式「Install Docker Engine on Ubuntu」

5. tamanegi（外部カレンダー）の構築

先にtamanegiを起動し、JSONの受信先を用意します。以下はtamanegiサーバーで実行してください。

5-1. 正しいフォルダへ移動

cd /opt/kptc-tamanegi-build/260725_GW_WEB
pwd
ls docker/tamanegi/Dockerfile
ls 02_release/tamanegi/index.html

5-2. tamanegi用イメージを作る

sudo docker build \
  -f docker/tamanegi/Dockerfile \
  -t kptc-tamanegi:latest \
  .

最後の.は「現在のフォルダ一式を構築材料にする」という意味です。省略しないでください。

sudo docker image ls kptc-tamanegiでkptc-tamanegi latestが表示されれば成功です。

5-3. 実環境設定を作る

sudo mkdir -p /etc/kptc
sudo cp docker/tamanegi/tamanegi.env.example /etc/kptc/tamanegi.env
sudo chmod 600 /etc/kptc/tamanegi.env
sudo nano /etc/kptc/tamanegi.env

内容を次のようにします。値は例のまま使わず、2章で作成した公開JSON連携用の秘密値へ置き換えてください。

KPTC_PUBLIC_AVAILABILITY_SECRET=ここにoriginと共通の64文字の秘密値
KPTC_PUBLIC_AVAILABILITY_STALE_SECONDS=1800

nanoでは、保存はCtrl＋O、Enter、終了はCtrl＋Xです。

5-4. 保存場所を作り、コンテナを起動

sudo docker volume create kptc-tamanegi-data

sudo docker run -d \
  --name kptc-tamanegi \
  --restart unless-stopped \
  --env-file /etc/kptc/tamanegi.env \
  -p 127.0.0.1:8081:80 \
  -v kptc-tamanegi-data:/var/lib/kptc-availability \
  kptc-tamanegi:latest

127.0.0.1:8081:80は、サーバー内の8081番をコンテナのWeb画面へつなぎ、外部から8081番へ直接入れない指定です。外部からのHTTPS接続は7章のnginxを通します。

sudo docker psでkptc-tamanegiの状態がUp、少し待つとhealthyになれば成功です。

5-5. サーバー内から確認

curl -I http://127.0.0.1:8081/
sudo docker logs --tail 50 kptc-tamanegi

最初は公開JSONがまだ届いていないため、画面に「空き状況を準備しています」と出る場合があります。これは故障ではありません。

6. origin（内部スケジューラ）の構築

以下はoriginサーバーで実行してください。

6-1. 正しいフォルダへ移動

cd /opt/kptc-origin-build/260725_GW_WEB
pwd
ls docker/origin/Dockerfile
ls 02_release/origin/index.php

6-2. origin用イメージを作る

sudo docker build \
  -f docker/origin/Dockerfile \
  -t kptc-origin:latest \
  .

この処理でPHP 8.4、Apache、SQLite、cURL、日本語処理機能とスケジューラのビルド後ファイルが1つのイメージになります。

sudo docker image ls kptc-originでkptc-origin latestが表示されれば成功です。

6-3. 実環境設定を作る

sudo mkdir -p /etc/kptc
sudo cp docker/origin/origin.env.example /etc/kptc/origin.env
sudo chmod 600 /etc/kptc/origin.env
sudo nano /etc/kptc/origin.env

例を実際のURLと秘密値へ置き換えます。

KPTC_PORTAL_TOKEN_KEY=既存社内システムと共通の秘密値
KPTC_PUBLIC_AVAILABILITY_ENDPOINT=https://calendar.example.jp/receive-availability.php
KPTC_PUBLIC_AVAILABILITY_PAGE_URL=https://calendar.example.jp/
KPTC_PUBLIC_AVAILABILITY_SECRET=tamanegiと共通の64文字の秘密値
KPTC_SESSION_COOKIE_SECURE=1
KPTC_AUTH_IDLE_TIMEOUT=1800
KPTC_AUTH_ABSOLUTE_TIMEOUT=43200
送信先の指定場所：tamanegiのIPアドレスをDockerfileへ書くのではなく、ここにあるKPTC_PUBLIC_AVAILABILITY_ENDPOINTへtamanegiのHTTPS受信URLを指定します。URLが変わった場合はこのファイルだけを直してコンテナを作り直せます。
トークン鍵の日付：KPTC_PORTAL_TOKEN_KEYには固定部分だけを書きます。プログラムが実行時にUTC当日をgmdate('Ymd')で付加します。社内システム側も同じ固定部分と同じ方式を使用してください。

6-4. 保存場所を作り、コンテナを起動

sudo docker volume create kptc-origin-data

sudo docker run -d \
  --name kptc-origin \
  --restart unless-stopped \
  --env-file /etc/kptc/origin.env \
  -p 127.0.0.1:8080:80 \
  -v kptc-origin-data:/var/lib/kptc-scheduler \
  kptc-origin:latest

sudo docker psでkptc-originがUp、少し待つとhealthyになれば成功です。

6-5. PHP機能を確認

sudo docker exec kptc-origin php -v
sudo docker exec kptc-origin php -m | grep -E 'curl|mbstring|openssl|pdo_sqlite|sqlite3'

PHP 8.4と、上記5種類の機能名が表示されることを確認します。

7. URL・HTTPSの設定

Dockerコンテナはサーバー内部のHTTPポートで待ち受けます。利用者がアクセスするHTTPS URLは、ホスト側のnginxなどからコンテナへ中継します。以下は考え方を示す最小例です。証明書の取得方法は組織の規則に従ってください。

7-1. nginxを導入

sudo apt update
sudo apt install -y nginx

7-2. origin側の中継例

/etc/nginx/sites-available/kptc-originを作成します。証明書パスとドメインは実環境へ変更してください。

server {
    listen 443 ssl;
    server_name scheduler.example.local;

    ssl_certificate     /etc/ssl/certs/origin-fullchain.pem;
    ssl_certificate_key /etc/ssl/private/origin-key.pem;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto https;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}

7-3. tamanegi側の中継例

/etc/nginx/sites-available/kptc-tamanegiを作成します。

server {
    listen 443 ssl;
    server_name calendar.example.jp;

    ssl_certificate     /etc/ssl/certs/tamanegi-fullchain.pem;
    ssl_certificate_key /etc/ssl/private/tamanegi-key.pem;

    client_max_body_size 128k;

    location / {
        proxy_pass http://127.0.0.1:8081;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto https;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}

7-4. 設定を有効にする

# originで実行
sudo ln -s /etc/nginx/sites-available/kptc-origin /etc/nginx/sites-enabled/kptc-origin
sudo nginx -t
sudo systemctl reload nginx

# tamanegiで実行
sudo ln -s /etc/nginx/sites-available/kptc-tamanegi /etc/nginx/sites-enabled/kptc-tamanegi
sudo nginx -t
sudo systemctl reload nginx
公開範囲：originはファイアウォール、VPN、社内ネットワーク制限などで外部から接続できないようにしてください。tamanegiは443番だけを公開し、8081番は外部へ公開しません。

9. 現在のSQLiteデータをoriginへ移す場合

新規構築だけならこの章は飛ばしてください。既存SQLiteを移す場合は、コピー中に予定が変わらないよう、移行時間を利用者へ案内してから行います。

  1. 既存システムを編集停止にする
  2. 既存SQLiteのバックアップを別名で保存する
  3. originコンテナを停止する
  4. SQLiteをコンテナの永続保存場所へコピーする
  5. originコンテナを起動する
# originサーバーで実行
sudo docker stop kptc-origin
sudo docker cp /安全な移行元/group-watcher.sqlite \
  kptc-origin:/var/lib/kptc-scheduler/group-watcher.sqlite
sudo docker start kptc-origin
sudo docker logs --tail 50 kptc-origin
注意：既存SQLiteの移行前に、新規環境で作られた予定を登録しないでください。どちらを正とするか分からなくなります。元ファイルは動作確認が終わるまで削除しないでください。

10. 更新・停止・バックアップ

10-1. 状態を見る

sudo docker ps
sudo docker logs --tail 100 kptc-origin
sudo docker logs --tail 100 kptc-tamanegi

10-2. 本番稼働後に修正・機能追加を反映する

初期構築後の修正も、サーバー上のPHPやJavaScriptを直接書き換えず、開発用PCで修正 → 試験 → ビルド → GitHubのmainへ反映 → 対象サーバーで再構築の順で行います。これにより、どの版を本番へ置いたかを後から確認でき、問題時に前の版へ戻せます。

10-2-1. 変更する側を決める

変更内容更新するサーバー
予定表、管理画面、認証、SQLite保存処理originだけ
外部公開カレンダーの表示、画像、受信処理tamanegiだけ
originから送る公開JSONの形式原則としてtamanegiを先に更新し、その後origin
既存社内システムの入口・トークン発行社内システム担当者の環境。模擬renkonは本番へ設置しない
別サーバーであることを忘れない：originだけの修正ならtamanegiの再構築は不要です。両方を変更する場合も、それぞれのサーバーへ接続して別々に作業します。

10-2-2. 開発用PCで修正・試験・ビルド

01_sourceが人が修正する原本、02_releaseがサーバーへ入れるビルド後ファイルです。02_releaseだけを直接修正すると、次回ビルド時に上書きされるため避けてください。

開発用PCにはGit、Node.js 22.13以降、pnpmを用意します。最初にnode --versionとpnpm --versionで確認し、命令が見つからない場合はNode.jsとpnpmを導入してから進みます。

cd 260725_GW_WEB
git switch main
git pull --ff-only origin main
git switch -c feature/scheduler-change

cd 01_source
pnpm install --frozen-lockfile
pnpm test
pnpm run check
pnpm run build
cd ..

git status --short
git diff --check

pnpm run buildは、origin・tamanegi・模擬renkonの配布ファイルを02_releaseへ作り直します。試験に失敗した場合は本番へ進まず、原因を直して再実行します。

git add 01_source 02_release
git commit -m "feat: describe the scheduler change"
git push origin feature/scheduler-change

GitHub上で変更内容と試験結果を確認してmainへ統合します。緊急時でも、秘密値、SQLite、実環境のenvファイル、公開中JSONはGitHubへ追加しません。

10-2-3. origin更新前のバックアップ

利用者へ短時間の更新作業を案内し、originサーバーで現在の版とデータを控えます。下のYYYYMMDD-HHMMは、実際の更新日時（例：20261003-1900）へ置き換えます。

cd /opt/kptc-origin-build/260725_GW_WEB
git status --short
git rev-parse --short HEAD

sudo install -d -m 700 /var/backups/kptc
sudo docker exec kptc-origin \
  php /var/www/html/backup-scheduler-cli.php

sudo docker exec kptc-origin php -r '
$source = new SQLite3("/var/lib/kptc-scheduler/group-watcher.sqlite", SQLITE3_OPEN_READONLY);
$backup = new SQLite3("/var/lib/kptc-scheduler/backups/pre-update-YYYYMMDD-HHMM.sqlite");
if (!$source->backup($backup)) { exit(1); }
'
sudo docker cp \
  kptc-origin:/var/lib/kptc-scheduler/backups/pre-update-YYYYMMDD-HHMM.sqlite \
  /var/backups/kptc/
sudo chmod 600 /var/backups/kptc/pre-update-YYYYMMDD-HHMM.sqlite

sudo docker image tag \
  kptc-origin:latest kptc-origin:rollback-YYYYMMDD-HHMM

git status --shortが空で、SQLiteバックアップが存在し、戻すためのDockerイメージタグが作られてから更新へ進みます。差分が表示された場合は、サーバー上で誰かがファイルを直接変更しているため、上書きせず管理者へ確認します。

10-2-4. originへmainの最新版を反映

cd /opt/kptc-origin-build/260725_GW_WEB
git switch main
git pull --ff-only origin main
git rev-parse --short HEAD

sudo docker build -f docker/origin/Dockerfile -t kptc-origin:latest .
sudo docker stop kptc-origin
sudo docker rm kptc-origin

sudo docker run -d \
  --name kptc-origin \
  --restart unless-stopped \
  --env-file /etc/kptc/origin.env \
  -p 127.0.0.1:8080:80 \
  -v kptc-origin-data:/var/lib/kptc-scheduler \
  kptc-origin:latest

通常のプログラム更新では、/etc/kptc/origin.envを作り直しません。新しい環境変数が追加された場合だけ、リポジトリ内のdocker/origin/origin.env.exampleと変更説明を確認して追記します。既存の秘密値を新しいランダム値へ勝手に変更すると、社内入口やtamanegiとの通信が止まります。

10-2-5. tamanegiを更新する場合

外部カレンダー側も変更した場合だけ、tamanegiサーバーで同じ流れを実施します。公開JSON形式を変更した場合は、旧形式も受信できるtamanegiを先に反映してからoriginを更新します。

cd /opt/kptc-tamanegi-build/260725_GW_WEB
git status --short
git rev-parse --short HEAD
sudo docker image tag \
  kptc-tamanegi:latest kptc-tamanegi:rollback-YYYYMMDD-HHMM

git switch main

sudo docker build -f docker/tamanegi/Dockerfile -t kptc-tamanegi:latest .
sudo docker stop kptc-tamanegi
sudo docker rm kptc-tamanegi

sudo docker run -d \
  --name kptc-tamanegi \
  --restart unless-stopped \
  --env-file /etc/kptc/tamanegi.env \
  -p 127.0.0.1:8081:80 \
  -v kptc-tamanegi-data:/var/lib/kptc-availability \
  kptc-tamanegi:latest

10-2-6. 更新後の確認

  1. sudo docker psで対象コンテナがUp、その後healthyになることを確認
  2. sudo docker logs --since 10m コンテナ名で連続エラーがないことを確認
  3. 既存社内システム経由でoriginを開き、予定の追加・編集・移動・削除を各1回確認
  4. 確認用予定を削除し、画面上部が共有保存済みになることを確認
  5. 試験室予定に関係する変更では、tamanegiの表示とhealth-availability.phpのHTTP 200を確認
  6. 利用者へ更新完了と、問題時の連絡先を案内
sudo docker ps
sudo docker logs --since 10m kptc-origin
curl -i https://calendar.example.jp/health-availability.php

10-2-7. 問題が起きた場合の切戻し

新しい版で操作不能や保存異常が発生した場合は、無理に本番データを編集せず、更新前イメージへ戻します。次はoriginの例です。

sudo docker stop kptc-origin
sudo docker rm kptc-origin
sudo docker run -d \
  --name kptc-origin \
  --restart unless-stopped \
  --env-file /etc/kptc/origin.env \
  -p 127.0.0.1:8080:80 \
  -v kptc-origin-data:/var/lib/kptc-scheduler \
  kptc-origin:rollback-YYYYMMDD-HHMM

プログラムだけの切戻しでは名前付きボリュームをそのまま使います。更新によってDB形式まで変わり、旧版で読めない場合に限り、利用を停止して更新前SQLiteから復元します。復元方法は、既存の独立Linuxサーバー構築・移行手順書に従い、復元後に公開JSONを再送します。

実行禁止：docker volume rm、docker compose down -v、SQLiteの直接上書きを、バックアップ確認前に実行しないでください。
データが残る理由：docker rmでコンテナを消しても、名前付きボリュームは残ります。本書の命令では-vを付けて削除しません。

10-3. 停止と再開

sudo docker stop kptc-origin
sudo docker start kptc-origin

sudo docker stop kptc-tamanegi
sudo docker start kptc-tamanegi

10-4. originの最新JSONバックアップ確認

sudo docker exec kptc-origin \
  php /var/www/html/backup-scheduler-cli.php
sudo docker exec kptc-origin \
  ls -l /var/lib/kptc-scheduler/backups/scheduler-latest.json

名前付きボリュームは同じサーバーの故障には備えられません。運用開始後は、組織のバックアップ製品などでoriginのボリュームまたはバックアップJSONを別の安全な保存先へ複製してください。

参照：Docker公式「docker container run」、Docker公式「docker volume create」

10.5 Docker Compose版で構築する場合（推奨）

5章・6章のdocker run方式に代えて、設定をYAMLファイルへまとめるDocker Compose方式でも運用できます。通常の起動・更新を短い命令で行えるため、新しく構築する場合はこの方式を推奨します。

方式はどちらか一方：docker run方式とDocker Compose方式を同時に起動しないでください。同じコンテナ名とポートを使うため競合します。Compose方式を選ぶ場合も、originとtamanegiは必ず別サーバーへ構築します。

10.5-1. tamanegi用Composeファイルを作る

tamanegiサーバーで、tamanegi用リポジトリの最上位へ移動し、compose.tamanegi.yamlを作ります。

cd /opt/kptc-tamanegi-build/260725_GW_WEB
nano compose.tamanegi.yaml

次の内容を貼り付け、Ctrl＋O、Enter、Ctrl＋Xの順で保存します。

services:
  kptc-tamanegi:
    container_name: kptc-tamanegi
    build:
      context: .
      dockerfile: docker/tamanegi/Dockerfile
    image: kptc-tamanegi:latest
    restart: unless-stopped
    env_file:
      - /etc/kptc/tamanegi.env
    ports:
      - "127.0.0.1:8081:80"
    volumes:
      - kptc-tamanegi-data:/var/lib/kptc-availability

volumes:
  kptc-tamanegi-data:
    name: kptc-tamanegi-data

/etc/kptc/tamanegi.envは5-3で作成した実環境設定です。まだ作成していない場合は、先に5-3を実施してください。

10.5-2. origin用Composeファイルを作る

originサーバーで、origin用リポジトリの最上位へ移動し、compose.origin.yamlを作ります。

cd /opt/kptc-origin-build/260725_GW_WEB
nano compose.origin.yaml

次の内容を貼り付けて保存します。

services:
  kptc-origin:
    container_name: kptc-origin
    build:
      context: .
      dockerfile: docker/origin/Dockerfile
    image: kptc-origin:latest
    restart: unless-stopped
    env_file:
      - /etc/kptc/origin.env
    ports:
      - "127.0.0.1:8080:80"
    volumes:
      - kptc-origin-data:/var/lib/kptc-scheduler

volumes:
  kptc-origin-data:
    name: kptc-origin-data

/etc/kptc/origin.envは6-3で作成した実環境設定です。まだ作成していない場合は、先に6-3を実施してください。

10.5-3. 既存のdocker run方式から切り替える場合

5-4または6-4ですでにコンテナを起動している場合だけ、対象サーバーで既存コンテナを停止して削除します。名前付きボリュームは削除しないため、同じ名前のボリュームをComposeで接続すれば保存データを引き継げます。

# tamanegiサーバーで実行
sudo docker stop kptc-tamanegi
sudo docker rm kptc-tamanegi

# originサーバーで実行
sudo docker stop kptc-origin
sudo docker rm kptc-origin

新規構築で、まだコンテナを起動していない場合、この手順は不要です。

10.5-4. 構成確認と起動

まずYAMLの書き方と実環境設定を確認し、問題がなければ構築して起動します。それぞれのサーバーで自分用の命令だけを実行してください。

# tamanegiサーバーで実行
cd /opt/kptc-tamanegi-build/260725_GW_WEB
sudo docker compose -f compose.tamanegi.yaml config
sudo docker compose -f compose.tamanegi.yaml up -d --build
sudo docker compose -f compose.tamanegi.yaml ps

# originサーバーで実行
cd /opt/kptc-origin-build/260725_GW_WEB
sudo docker compose -f compose.origin.yaml config
sudo docker compose -f compose.origin.yaml up -d --build
sudo docker compose -f compose.origin.yaml ps

各サーバーのpsで対象コンテナがUp、少し待つとhealthyになれば起動成功です。続いて7章のHTTPS設定と11章のブラウザ確認を行います。

10.5-5. 更新・再起動・停止

更新時は、先に10-2の「変更する側の判断」「開発用PCでの試験・ビルド」「更新前バックアップ」を実施します。その後、対象サーバーでGitHubから最新版を取得し、同じComposeファイルを指定して再構築します。

# tamanegiサーバーで更新
cd /opt/kptc-tamanegi-build/260725_GW_WEB
sudo docker image tag kptc-tamanegi:latest \
  kptc-tamanegi:rollback-YYYYMMDD-HHMM
git pull --ff-only origin main
sudo docker compose -f compose.tamanegi.yaml up -d --build

# originサーバーで更新
cd /opt/kptc-origin-build/260725_GW_WEB
sudo docker image tag kptc-origin:latest \
  kptc-origin:rollback-YYYYMMDD-HHMM
git pull --ff-only origin main
sudo docker compose -f compose.origin.yaml up -d --build

# 起動状態とログを確認
sudo docker compose -f compose.origin.yaml ps
sudo docker compose -f compose.origin.yaml logs --since 10m

切戻す場合は、更新前タグをlatestへ付け直し、ビルドせずにコンテナを作り直します。次はoriginの例です。

sudo docker image tag \
  kptc-origin:rollback-YYYYMMDD-HHMM kptc-origin:latest
sudo docker compose -f compose.origin.yaml \
  up -d --no-build --force-recreate

再起動と停止・再開は次の命令です。先頭のファイル名は、作業中のサーバーに合わせます。

sudo docker compose -f compose.origin.yaml restart
sudo docker compose -f compose.origin.yaml stop
sudo docker compose -f compose.origin.yaml start
保存データを守る：通常運用ではdocker compose down -vを実行しないでください。末尾の-vは名前付きボリュームも削除する指定であり、SQLiteまたは公開JSONが失われます。

参照：Docker公式「Docker Compose」、Docker公式「docker compose up」

11. Webブラウザで閲覧・操作できるまで

この章は、前章までの構築を終えた後、実際に利用者がWebブラウザでスケジューラと空き状況を使える状態へ進める最終手順です。上から順に確認してください。

11-1. 先にtamanegiの公開URLを確認

社内または外部のパソコンで、Chrome、Edge、Safariなどを開き、tamanegiの公開URLを入力します。

https://calendar.example.jp/

ページ自体が表示されれば、Webブラウザからtamanegiまでの経路は完成です。まだJSONが届いていない場合の「空き状況を準備しています」という表示は正常です。

ターミナルからは次も確認できます。

curl -I https://calendar.example.jp/
curl -i https://calendar.example.jp/receive-availability.php
確認先構築直後の正常な結果
tamanegiトップページHTTP 200、空き状況画面を表示
receive-availability.phpをGETで確認HTTP 405。受信口がPOSTだけを受け付けるため正常
health-availability.php初回JSON受信前はHTTP 503、受信後はHTTP 200

11-2. originの直接アクセス拒否を確認

WebブラウザでoriginのURLを直接開きます。

https://scheduler.example.local/

ForbiddenまたはHTTP 403になれば正常です。この結果は故障ではなく、社内システムを通らないアクセスを拒否できている証拠です。

11-3. 既存社内システムへorigin入口を組み込む

この作業は、既存社内システムの開発担当者が社内システム側で行います。本番環境へ模擬サイトrenkonを設置する作業ではありません。ログイン済み利用者の3桁IDから暗号化トークンを作り、originへ移動するリンクまたはボタンを追加します。

本人確認に関する条件：3桁IDをURLや入力欄からそのまま受け取らず、既存社内システムがログイン済み利用者について保持しているIDを使用してください。利用者が別人のIDへ書き換えられる実装は不可です。

社内システム担当者へ、次の仕様を渡します。

項目仕様
利用者情報user_＋ログイン済み利用者の半角数字3桁ID。例：user_007
暗号方式AES-256-CBC
鍵hash('sha256', 固定秘密値 . gmdate('Ymd'), true)
IV毎回新しく作る16バイトの安全な乱数
トークンBase64(IV＋暗号文)
移動先https://scheduler.example.local/?token=URLエンコードしたトークン
共有設定社内システムとoriginのKPTC_PORTAL_TOKEN_KEYへ同じ固定秘密値

実装の原本はGitHub内の次の2ファイルです。社内システム担当者は暗号処理を参考にし、IDの取得部分だけを既存ログイン情報へ置き換えます。

02_release/renkon/open-scheduler.php
02_release/renkon/renkon-config.php
日付切り替え：鍵へ付ける日付は必ずPHPのgmdate('Ymd')によるUTC当日です。社内システム側とorigin側で日付や固定秘密値が異なると、正しい利用者でもForbiddenになります。

11-4. 管理者パスワードを初期設定

originサーバーで次を実行し、管理者モード用パスワードを設定します。パスワードは8～128文字です。

sudo docker exec -it kptc-origin \
  php /var/www/html/manage-auth-user-cli.php set-admin-mode-password

入力中の文字は画面に表示されません。Admin mode password updated.が表示されれば完了です。

11-5. 社内システムからスケジューラを開く

  1. 社内ネットワークに接続したパソコンでWebブラウザを開く
  2. 既存社内システムへ通常のユーザー名とパスワードでログイン
  3. 追加した「スケジューラ」リンクまたはボタンを選択
  4. ログイン画面を挟まず、KPTC Schedulerの今週の予定表が表示されることを確認

ブラウザのアドレスに一時的な?token=...が付き、スケジュール画面が表示されれば入口連携の成功です。トークンや秘密値を画面写真・メールへ載せないでください。

11-6. 一般モードの操作試験

確認用の予定を1件作り、編集後に削除します。実際の予定と区別できる件名を使用してください。

  1. 日付の枠をダブルクリック
  2. ユーザー、予定種別、開始日・終了日、時間帯を設定
  3. 件名を「Docker構築確認」として登録
  4. 予定ブロックを開いて時間を変更
  5. ドラッグ＆ドロップし、確認メッセージで移動を承認
  6. 右クリックまたはDeleteキーで確認用予定を削除

登録、変更、移動、削除がすべて成功すれば、ブラウザからoriginのSQLiteへ保存できています。

11-7. 管理者モードの操作試験

  1. スケジュール画面の「管理者モード」を選択
  2. 11-4で設定した管理者パスワードを入力
  3. ユーザー・試験室・予定種別の管理画面が表示されることを確認
  4. 操作履歴が表示されることを確認
  5. 確認後は一般モードへ戻る

本番データを不用意に変えないよう、管理項目は表示確認だけに留めても構いません。

11-8. originからtamanegiへの反映試験

試験室ユーザーに、未来の日付で「機器利用」の確認用予定を登録します。その後、すぐ確認する場合はoriginサーバーで手動送信します。

sudo docker exec kptc-origin \
  php /var/www/html/publish-availability-cli.php

Webブラウザでtamanegiを再読み込みし、該当する試験室・日付の表示が変わることを確認します。通常は予定保存時にも送信を試み、失敗した場合は5分ごとの処理で再送します。

curl -i https://calendar.example.jp/health-availability.php
sudo docker logs --since 10m kptc-origin
sudo docker logs --since 10m kptc-tamanegi

tamanegiのhealth-availability.phpがHTTP 200で、公開画面に予定の空き状態が反映されれば、別サーバー間のJSON連携成功です。確認後は確認用予定をoriginで削除し、再送後に公開画面も元へ戻ることを確認します。

11-9. 再起動後もデータが残ることを確認

利用開始前の確認時間に、各サーバーで自分のコンテナだけを再起動します。

# originサーバーで実行
sudo docker restart kptc-origin

# tamanegiサーバーで実行
sudo docker restart kptc-tamanegi

再度Webブラウザで両画面を開き、予定と公開カレンダーが残っていることを確認します。これは名前付きDockerボリュームが正しく接続されていることの確認です。

11-10. 利用開始の合格表

  • originとtamanegiが別サーバーで稼働
  • 両コンテナがhealthy
  • tamanegiをHTTPSの公開URLで表示可能
  • originへの直接アクセスがHTTP 403
  • 既存社内システム経由でoriginを表示可能
  • 一般モードで予定の登録・編集・移動・削除が可能
  • 管理者モードへ切り替え可能
  • originの試験室予定がtamanegiへ反映
  • コンテナ再起動後もデータを維持
  • 毎日22時のバックアップ保存先を確認
利用開始：上の10項目をすべて確認できた時点で、Webブラウザからの閲覧・操作を開始できる状態です。

13. 用語集

用語やさしい説明
Dockerプログラムと動作に必要な道具を、ひとまとめの箱として動かす仕組み。
Dockerfileその箱をどのように作るか、順番を書いた設計図。
イメージDockerfileから作った、まだ動いていない完成済みの箱の型。
コンテナイメージをもとに実際に動いているプログラムの箱。
ボリューム箱を作り直しても消えないよう、データを箱の外側へ保管する場所。
環境変数・envファイル送信先URLや秘密値など、設置場所ごとに違う設定をプログラムへ渡す方法。
origin予定の元データを持つ社内側サーバーの呼び名。
tamanegi公開してよい空き状況だけを外部へ見せるサーバーの呼び名。
SQLite予定を1つのファイルへ整理して保存するデータベース。
JSONコンピューター同士が項目と値を分かりやすく受け渡すための文章形式。
HTTPS通信内容を暗号化して、途中で読まれにくくするWeb通信。
DNScalendar.example.jpのような名前とIPアドレスを結び付ける案内帳。
