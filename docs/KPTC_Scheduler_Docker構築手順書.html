1. 構成の全体像

Originサーバー1台の中で、スケジューラと公開カレンダーを分離して動かします。サーバーは同じでも、SQLiteと公開JSONは別の保存領域です。

利用者社内利用者または一般閲覧者
→
管理者のリバースプロキシ/Scheduler/はIP制限
/Calendar/は一般公開
→
OriginサーバーSchedulerコンテナ
Calendarコンテナ
区分公開パスコンテナ保存する情報
内部スケジューラ/Scheduler/kptc-scheduler予定、利用者、設定、JSONバックアップ
公開カレンダー/Calendar/kptc-calendar公開してよい直近3か月の空き状況JSON
データ連携：Schedulerは予定を保存すると、公開可能な試験室情報だけを署名付きJSONに変換し、Docker内部ネットワークのhttp://kptc-calendar/receive-availability.phpへ送ります。CalendarがSQLiteを直接読む構成ではありません。

SchedulerとCalendarは、利用者から見えるURL上のディレクトリです。実体は同じOriginサーバー内の2コンテナで、管理者のリバースプロキシが各URLを対応するコンテナへ中継します。OS上へ同名の公開フォルダを作る必要はありません。

1-1. 詳細論理構成図

青線は利用者のアクセス、緑線は予定・公開情報の流れ、オレンジ色の点線はGitHubから実行環境を更新する流れです。赤い点線内はWebから直接公開しない保存領域です。

  • ブラウザからのアクセス
  • 予定・公開情報の流れ
  • 配布・更新の流れ
  • Webから直接公開しない領域
  1. 社内から利用：既存社内システムが利用者IDを暗号化したtokenを付け、IP制限された/Scheduler/へ移動します。
  2. 予定を保存：SchedulerのAPIが権限とCSRFを確認し、予定をSQLiteへ保存します。管理者モードだけが利用者・部屋・管理者パスワードを変更できます。
  3. 公開情報を連携：試験室予定から公開可能な直近3か月分だけを生成し、HMAC署名を付けてDocker内部ネットワークからCalendarへ送ります。
  4. 一般公開：閲覧者は/Calendar/へアクセスし、公開用JSONだけを参照します。内部SQLiteを直接読むことはありません。
  5. 更新・保守：GitHubの同じコミットに含まれるビルド後ファイルから両コンテナを再構築し、SQLiteと公開JSONはDocker Volumeに保持します。
保存領域の分離：SchedulerのSQLiteとバックアップJSONはScheduler専用Volume、公開用3か月JSONはCalendar専用Volumeに保存します。CalendarからScheduler専用Volumeへの接続経路はなく、公開画面はpublic-availability.phpを通してCalendar側のJSONだけを読みます。
簡易参照資料：Docker構成と主要コマンドだけを短く確認したい場合は、リポジトリ内のdocker/README.mdを参照してください。構築作業では本HTML手順書を正式な手順とし、内容に差がある場合は本書を優先します。
表記：カレンダーの英語表記はCalendarに統一しています。LinuxのパスとURLでは大文字・小文字を区別するため、公開パスは/Calendar/を使用してください。

2. 事前準備

  • Ubuntu 24.04のOriginサーバー1台
  • 管理者権限を持つ作業用アカウント
  • GitHubから本リポジトリを取得できる通信
  • HTTPSで使用するOriginサーバーのホスト名
  • 社内入口と同じKPTC_PORTAL_TOKEN_KEYの固定部分
  • 32文字以上の公開JSON連携用秘密値
  • 管理者が設定するIP許可範囲
秘密値の扱い：実値をGitHub、手順書、メール、画面写真へ載せません。実環境設定は/etc/kptc/へ置き、管理者だけが読める権限にします。

4. Dockerの導入

Dockerが未導入の場合のみ、Originサーバーで次を実行します。

sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
  -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo $VERSION_CODENAME) stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io \
  docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
sudo docker version
sudo docker compose version

DockerとDocker Composeのバージョンが表示されれば準備完了です。

5. 実環境設定

5-1. 設定ファイルを作る

sudo install -d -m 700 /etc/kptc
sudo cp docker/origin/Scheduler/scheduler.env.example /etc/kptc/scheduler.env
sudo cp docker/origin/Calendar/calendar.env.example /etc/kptc/calendar.env
sudo chmod 600 /etc/kptc/scheduler.env /etc/kptc/calendar.env
sudo nano /etc/kptc/scheduler.env

5-2. Scheduler側の値

KPTC_PORTAL_TOKEN_KEY=社内入口と共通の十分に長い固定文字列
KPTC_PUBLIC_AVAILABILITY_MODE=https
KPTC_PUBLIC_AVAILABILITY_ENDPOINT=http://kptc-calendar/receive-availability.php
KPTC_PUBLIC_AVAILABILITY_PAGE_URL=https://origin.example.jp/Calendar/
KPTC_PUBLIC_AVAILABILITY_SECRET=32文字以上のランダムな共通秘密値
KPTC_PUBLIC_AVAILABILITY_ALLOW_HTTP=1
KPTC_PUBLIC_AVAILABILITY_TIMEOUT=10
KPTC_PUBLIC_AVAILABILITY_STALE_SECONDS=1800
KPTC_SESSION_COOKIE_SECURE=1
KPTC_SESSION_COOKIE_PATH=/Scheduler/
KPTC_AUTH_IDLE_TIMEOUT=1800
KPTC_AUTH_ABSOLUTE_TIMEOUT=43200
  • origin.example.jpは実際のホスト名へ変更します。
  • KPTC_PUBLIC_AVAILABILITY_ALLOW_HTTP=1は、同じOriginサーバー内の閉じたDockerネットワークでHTTP通信するための指定です。外部へHTTP公開する許可ではありません。
  • KPTC_SESSION_COOKIE_PATH=/Scheduler/により、認証Cookieを公開カレンダー側へ送らないよう範囲を限定します。

5-3. Calendar側の値

sudo nano /etc/kptc/calendar.env
KPTC_PUBLIC_AVAILABILITY_SECRET=Scheduler側と同じ32文字以上の秘密値
KPTC_PUBLIC_AVAILABILITY_STALE_SECONDS=1800

2つの設定ファイルでKPTC_PUBLIC_AVAILABILITY_SECRETが完全一致し、どちらにもREPLACE_が残っていないことを確認します。

5-4. 環境ごとに決める変数

次の表は、/etc/kptc/scheduler.envと/etc/kptc/calendar.envで利用者が決める値、または必要に応じて変更できる値です。コマンドで秘密値を生成した場合、envファイルへコマンド自体を書かず、表示された文字列だけを貼り付けます。

変数名機能設定方法・例必須／任意
KPTC_PORTAL_TOKEN_KEY社内システムが発行するCBC暗号化tokenをSchedulerが復号するための元鍵。プログラムが末尾へUTC当日の日付を付けて日ごとの鍵を作る。openssl rand -hex 32で生成し、社内システム側とScheduler側へ同じ文字列を設定。日付は手入力しない。必須
KPTC_RENKON_SCHEDULER_URL既存社内システムまたは検証用renkonがtoken付きで移動するSchedulerのURL。https://origin.example.jp/Scheduler/。既存社内システム側の設定として、実際のホスト名と公開パスを指定。社内入口側で必須
KPTC_PUBLIC_AVAILABILITY_SECRETSchedulerからCalendarへ送る3か月JSONのHMAC-SHA256署名と検証に使う共有秘密値。openssl rand -hex 32で生成し、scheduler.envとcalendar.envへ完全に同じ値を設定。必須
KPTC_PUBLIC_AVAILABILITY_MODE公開JSONをローカル保存するか、受信APIへ送るかを選ぶ。httpsは「API送信モード」という名称で、エンドポイント自体がHTTPの場合にも使用する。本構成は別コンテナへ送るためhttps。localは単一PHP領域で直接ファイル保存する特殊構成だけに使用。必須（本構成はhttps）
KPTC_PUBLIC_AVAILABILITY_ENDPOINTCalendarの署名付きJSON受信APIのURL。同一Origin内の推奨値はhttp://kptc-calendar/receive-availability.php。TLS経由にする場合はhttps://origin.example.jp/Calendar/receive-availability.php。必須
KPTC_PUBLIC_AVAILABILITY_PAGE_URLScheduler画面の「試験室予約」から開く公開CalendarのURL。https://origin.example.jp/Calendar/のホスト名を実環境のものへ変更。必須
KPTC_PUBLIC_AVAILABILITY_ALLOW_HTTPJSON受信APIへのHTTP送信を明示的に許可する。閉じたDocker内部通信では1。HTTPSエンドポイントでは0または行を削除。HTTP時のみ必須
KPTC_SESSION_COOKIE_SECUREブラウザがHTTPS通信のときだけセッションCookieを送るかを指定する。本番HTTPSは1。閉じた試験環境でブラウザもHTTPを使う場合だけ0。必須
KPTC_SESSION_COOKIE_PATHSchedulerのCookieを送信するURL範囲。Calendarへ認証Cookieを送らないための設定。公開パスに合わせて/Scheduler/。Schedulerを別パスへ置く場合だけ変更。推奨（通常は変更不要）
KPTC_AUTH_IDLE_TIMEOUT操作がない状態でセッションを終了するまでの秒数。既定例は1800（30分）。最小値は300秒。任意
KPTC_AUTH_ABSOLUTE_TIMEOUT操作を続けていてもセッションを終了する最長時間。既定例は43200（12時間）。アイドル時間以上に設定。任意
KPTC_PUBLIC_AVAILABILITY_TIMEOUTSchedulerがCalendarへの送信完了を待つ秒数。既定値は10。3～60秒の範囲で通信環境に合わせて変更。任意
KPTC_PUBLIC_AVAILABILITY_STALE_SECONDS公開JSONを「更新が古い」と判定するまでの秒数。既定例は1800（30分）。監視間隔に合わせ、両側で同じ値を推奨。任意

次の保存先変数はDockerfileで設定済みです。保存先を別Volumeへ変更する場合に限り上書きします。

変数名既定値用途必須／任意
KPTC_INTERNAL_SCHEDULER_DB/var/lib/kptc-scheduler/group-watcher.sqliteSchedulerのSQLite保存先。任意（高度な設定）
KPTC_SCHEDULER_BACKUP_JSON/var/lib/kptc-scheduler/backups/scheduler-latest.json毎日22時の最新バックアップJSON保存先。任意（高度な設定）
KPTC_PUBLIC_AVAILABILITY_JSON/var/lib/kptc-availability/public-availability.jsonCalendar専用Volume内の公開用3か月JSON保存先。任意（高度な設定）
秘密値：KPTC_PORTAL_TOKEN_KEYとKPTC_PUBLIC_AVAILABILITY_SECRETは別の値を使います。実値をGitHub、HTML手順書、作業記録、画面写真へ載せません。envファイルの権限は600を維持します。

5-5. HTTPとHTTPSを切り替える

本システムには、利用者のブラウザからリバースプロキシまでの外部通信と、SchedulerからCalendarへJSONを送るDocker内部通信があります。別々に設定します。

外部通信をHTTPからHTTPSへ変更する場合

/etc/kptc/scheduler.envを次のように変更します。

変数変更前：HTTP試験変更後：HTTPS本番
KPTC_PUBLIC_AVAILABILITY_PAGE_URLhttp://origin.example.jp/Calendar/https://origin.example.jp/Calendar/
KPTC_SESSION_COOKIE_SECURE01

既存社内システムまたは検証用renkonのKPTC_RENKON_SCHEDULER_URLも、http://origin.example.jp/Scheduler/からhttps://origin.example.jp/Scheduler/へ変更します。

env変更後はOriginサーバーでコンテナを再作成します。envだけの変更ではイメージの再ビルドは不要です。

cd /opt/kptc/260725_GW_WEB
sudo docker compose -f compose.origin-single.yaml config --quiet
sudo docker compose -f compose.origin-single.yaml \
  up -d --force-recreate
sudo docker compose -f compose.origin-single.yaml ps
sudo docker compose -f compose.origin-single.yaml \
  logs --since 10m --tail 200

リバースプロキシ管理者は、正式なホスト名のサーバー証明書と秘密鍵をリバースプロキシへ配置し、443番ポートでTLSを終端します。80番ポートは443番への転送専用にするか閉じます。Host、X-Forwarded-For、X-Forwarded-Proto: https、クエリ文字列を保持してください。証明書と秘密鍵をScheduler・Calendarコンテナへコピーする必要はありません。外部ファイアウォールでは443番だけを公開し、8080番・8081番は引き続き127.0.0.1待受のままにします。

外部通信をHTTPSからHTTPへ戻す場合（閉じた試験環境のみ）

上表を逆に変更し、リバースプロキシで80番のHTTPを受けます。KPTC_SESSION_COOKIE_SECURE=0にしないとHTTPではセッションCookieが送られません。tokenとCookieを暗号化せず送るため、本番・社内LAN・VPNを含む実運用では使用しません。

Docker内部のJSON通信を切り替える場合

変数推奨：内部HTTPリバースプロキシ経由HTTPS
KPTC_PUBLIC_AVAILABILITY_MODEhttpshttps
KPTC_PUBLIC_AVAILABILITY_ENDPOINThttp://kptc-calendar/receive-availability.phphttps://origin.example.jp/Calendar/receive-availability.php
KPTC_PUBLIC_AVAILABILITY_ALLOW_HTTP10または行を削除

HTTPSへ変更する場合は、Schedulerコンテナから正式ホスト名を名前解決でき、証明書を検証できること、リバースプロキシが/Calendar/receive-availability.phpへのPOSTを許可することが必要です。内部HTTPでもHMAC署名・送信時刻・JSON形式を検証し、通信は外部へ公開されないDockerネットワークだけを通るため、同一Originサーバーでは内部HTTPを推奨します。

再作成後、JSON連携を確認します。

sudo docker exec kptc-scheduler \
  php /var/www/html/publish-availability-cli.php
curl -i https://origin.example.jp/Calendar/health-availability.php

送信結果が"ok":true、Calendarのヘルス確認がHTTP 200、ブラウザのSchedulerとCalendarがHTTPSで表示されれば切替完了です。

6. 構築と起動

リポジトリ最上位で、同梱のCompose定義を使います。

cd /opt/kptc/260725_GW_WEB
sudo docker compose -f compose.origin-single.yaml config --quiet
sudo docker compose -f compose.origin-single.yaml up -d --build
sudo docker compose -f compose.origin-single.yaml ps

kptc-schedulerとkptc-calendarの2行が表示され、しばらく待ってhealthyになれば起動成功です。

curl -i http://127.0.0.1:8080/
curl -i http://127.0.0.1:8081/health-availability.php
sudo docker compose -f compose.origin-single.yaml logs --tail 100

Schedulerのトップは正しいトークンがないとHTTP 403になる設計です。8080番の403はコンテナ異常を意味しません。Calendarのヘルス確認はHTTP 200が正常です。

個別のdocker runとの併用禁止：同じポート、コンテナ名、保存領域が競合するため、この手順ではCompose方式だけを使います。docker compose down -vは保存領域も削除するため、本番では実行しません。

7. リバースプロキシ管理者への特記事項

リバースプロキシの導入・設定変更はサーバー管理者が別途実施します。本手順では仮想リバースプロキシを作りません。管理者へ次の要件を伝えてください。

項目SchedulerCalendar
外側のパス/Scheduler//Calendar/
中継先http://127.0.0.1:8080/http://127.0.0.1:8081/
IP制御指定された特定IPだけ許可全IPを許可
公開方式HTTPS。8080・8081番は外部へ直接開放しない

7-1. パスと転送

  • 外側の/Scheduler/または/Calendar/を取り除き、各コンテナのルート/へ渡す構成
  • /Schedulerから/Scheduler/、/Calendarから/Calendar/へ転送する場合もクエリ文字列を保持
  • 特に/Scheduler/?token=...のtokenをリダイレクトや書換えで消さない設定
  • api.phpへのGET・POST、receive-availability.phpへのPOST、静的ファイルへのGETを通す設定

7-2. ヘッダー、Cookie、キャッシュ

  • Host、X-Forwarded-For、X-Forwarded-Protoの転送
  • X-Forwarded-Proto: httpsとなる構成
  • SchedulerのCookieパスを/Scheduler/から変更しない設定
  • api.php、receive-availability.php、public-availability.php、health-availability.php、JSON応答はキャッシュしない設定
  • ファイル名にハッシュを含むJS・CSS・画像だけを長期キャッシュできる設定
  • POST本文の上限は少なくとも2MB
IP制御の位置：アクセス制限はコンテナではなく管理者のリバースプロキシで、/Scheduler/だけに適用します。/Calendar/へ同じ制限を継承させないようにします。

9. 既存データの移行

新規構築では、初回起動時にSQLiteが自動作成されます。既存SQLiteを引き継ぐ場合だけ次を行います。

sudo docker compose -f compose.origin-single.yaml stop kptc-scheduler
sudo docker run --rm \
  -v kptc-scheduler-data:/target \
  -v /移行元フォルダ:/source:ro \
  alpine sh -c 'cp /source/group-watcher.sqlite /target/group-watcher.sqlite && chown 33:33 /target/group-watcher.sqlite'
sudo docker compose -f compose.origin-single.yaml start kptc-scheduler

公開JSONはSchedulerから再生成できるため、Calendarの過去ファイルを移す必要はありません。

JSONバックアップからの復元

SQLite破損時は、コンテナ内の復元ツールに最新版バックアップを指定します。実行前に対象SQLiteを別名コピーしてください。

sudo docker exec kptc-scheduler \
  cp /var/lib/kptc-scheduler/group-watcher.sqlite \
     /var/lib/kptc-scheduler/pre-restore.sqlite

sudo docker exec -it kptc-scheduler \
  php /var/www/html/tools/restore-schedule-backup.php \
  /var/lib/kptc-scheduler/backups/schedule-backup-latest.json

10. 更新・復旧・バックアップ

10-1. 通常更新

基本の流れは、開発用PCで修正 → 試験 → ビルド → GitHubのmainへ反映 → Originサーバーで再構築です。サーバー上で01_sourceを直接編集しません。

cd /opt/kptc/260725_GW_WEB
git fetch origin
git switch main
git pull --ff-only origin main

sudo docker image tag kptc-scheduler:latest \
  kptc-scheduler:rollback-YYYYMMDD-HHMM
sudo docker image tag kptc-calendar:latest \
  kptc-calendar:rollback-YYYYMMDD-HHMM

sudo docker compose -f compose.origin-single.yaml up -d --build
sudo docker compose -f compose.origin-single.yaml ps
sudo docker compose -f compose.origin-single.yaml logs --since 10m

01_sourceは開発用、02_releaseはビルド後のサーバー実行用です。配布ファイルを変更する更新では、両コンテナを同じコミットから再構築します。

10-2. 更新前のSQLite退避

sudo docker exec kptc-scheduler cp \

10-3. イメージを戻す場合

sudo docker compose -f compose.origin-single.yaml stop
sudo docker image tag kptc-scheduler:rollback-YYYYMMDD-HHMM kptc-scheduler:latest

sudo docker compose -f compose.origin-single.yaml \
  up -d --no-build --force-recreate

10-4. 定期バックアップ

Schedulerコンテナでは毎日22時に当日以降の予定をJSONへ上書き保存します。保存先はkptc-scheduler-data内です。過去版を増やさない設計ですが、サーバー障害にも備える場合は管理者のバックアップ製品でDockerボリューム自体を別媒体へ複製します。

11. Webブラウザで閲覧・操作できるまで

  1. 管理者がHTTPSと7章のリバースプロキシ設定を完了
  2. 社内の許可IPからhttps://origin.example.jp/Scheduler/へアクセス
  3. 既存社内システムがログイン済み利用者について保持しているIDから、CBC方式のBase64(IV＋暗号文)トークンを付けてSchedulerへ移動
  4. 予定の表示、追加、編集、移動、コピー、貼り付け、削除を確認
  5. 社外回線からhttps://origin.example.jp/Calendar/へアクセス
  6. 公開カレンダーに直近3か月の空き状況が表示されることを確認
  7. 社外回線から/Scheduler/へアクセスし、管理者のIP制御で拒否されることを確認
