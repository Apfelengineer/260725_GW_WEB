# 内部IDの採番方式

2026年11月9日：任意の内部IDを管理者が入力する機能は取り消し、所属別の自動採番とします。

| 所属 | ID |
|---|---|
| 電気通信係 | `e001`、`e002`…`e999` |
| 試験室 | `t001`、`t002`…`t999` |

## 既存DBの移行

更新後のスケジューラへ初めてアクセスした際、DB内の現在の表示順を使い、所属ごとに独立して採番します。途中に試験室が並んでいても、電気通信係の番号はその所属内だけで連続します。既に新体系で保存済みのDBを復元した場合は、採番済みのIDを維持します。

移行前に、DBの隣の非公開`backups/`へ`pre-id-scheme-日時-識別子.sqlite`を自動退避します。退避や整合性確認に失敗した場合はID移行を中止します。予定・アカウントの紐付け・表示順・氏名・パスワードは同じDB取引で保全し、移行済みの印により再実行を防止します。旧内部IDはメンバーの`legacyId`に保持します。

更新作業の前には、従来どおり管理者もDBとenvをバックアップしてください。自動退避ファイルには非公開情報が含まれるため、GitHubや公開フォルダへ置かないでください。

IDが変更された既存セッションは無効になります。更新後は古いタブを閉じ、社内入口から入り直し、必要なら管理者モードへ切り替えてください。

## 追加・並べ替え・所属変更

- 新規ユーザーは所属の続き番号をサーバーが決めます。内部IDの自由入力・編集はできません。
- 表示順の変更で採番済みIDは変わりません。
- 削除による欠番は埋めず、使用済み番号を通常の追加で再利用しません。採番カウンターはJSONバックアップでも保持します。
- 所属変更時は新しい所属の続き番号へ変更し、予定・アカウントも引き継ぎます。公開対象の試験室は誤った公開連携を防ぐため所属変更を禁止します。
- ID移行・所属ID変更をまたぐ過去操作の「取り消し」は禁止します。履歴の説明自体は残します。

管理者のユーザー編集画面で、現在の内部IDを読取り専用で確認できます。社内入口で入力する3桁のIDは別の仕組みであり、今回の採番変更では変更しません。

## カレンダー・変換ツール

公開JSONの試験室IDも`t001`等へ変更します。初期の3室は旧設定キー`m6`・`m7`・`m8`と`legacyId`を使って照合し、名称と既存画像ファイル`m6.png`等を保持します。これらの画像ファイル名は内部IDではないため変更しません。旧`?room=m6`等のリンクは画像との対応により新しいIDへ読み替えます。

追加する試験室を公開する場合は、`availability-room-config.php`の`kptc_public_room_keys()`へ新ID（例：`t004`）を登録し、対応する画像と必要な名称上書きを設定します。追加しただけで自動公開されるわけではありません。

オフライン変換ツールでは新しいユーザー一覧を参照し、登録先に`e001`・`t001`等を指定してください。過去に保存した取込JSONや変換済みJSONは自動書換えしません。旧IDを含むJSONを取り込む場合は、対応を確認してから新IDへ変換し直してください。DB全体の復元用バックアップは旧形式も読み込め、旧IDは復元後の初回アクセスで移行します。
